# Lesson 06 — Async SQLAlchemy & the Data Layer

**Track:** FastAPI (Surwill) · **Time:** ~2.5h · **Prerequisites:** lessons 01, 05; comfortable SQL
**Objectives:** understand the engine/session architecture in `app/db.py`, the model mixins, `lazy="raise"`, soft deletes, and the row-locking that guards the project's most important invariant.

---

## Why this matters

The data layer is where most production incidents are born: pool exhaustion,
N+1 queries, race conditions, orphaned sessions. It's also where Surwill's best
interview story lives — **"how do you stop two people reserving the same gift?"**
— answered with `SELECT … FOR UPDATE`. This lesson gives you the architecture
and that story, precisely.

## Theory

SQLAlchemy 2.x has two layers: **Core** (SQL expression language, connections,
pooling) and **ORM** (mapped classes, the `Session` unit-of-work). The async
variant wraps both: `create_async_engine` + `AsyncSession`, driven by an async
driver (**asyncpg** for Postgres).

The mental model that prevents 80% of mistakes:

- **Engine** — process-wide singleton owning the connection **pool**. Created once.
- **Session** — short-lived unit of work: identity map + transaction script.
  One per request (or per job), never shared across tasks.
- **flush vs commit** — `flush()` sends pending SQL (so autogenerated IDs
  appear) but keeps the transaction open; `commit()` flushes then commits.
- **expire_on_commit** — by default, committed objects expire and reload on next
  access (another query!); async apps set it `False` to avoid surprise lazy I/O
  after commit.

> "The Session establishes all conversations with the database and represents a
> 'holding zone' for all the objects which you've loaded or associated with it
> during its lifespan."
> — SQLAlchemy docs, https://docs.sqlalchemy.org/en/20/orm/session_basics.html

## The code, explained

### Engine and session factory (`app/db.py`)

```python
_db_url = settings.DATABASE_URL.replace("postgresql://", "postgresql+asyncpg://", 1)
_is_sqlite = _db_url.startswith("sqlite")

engine = create_async_engine(
    _db_url,
    echo=not settings.is_production,
    **({} if _is_sqlite else {"pool_pre_ping": True, "pool_size": 10, "max_overflow": 20}),
)

AsyncSessionLocal = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)

async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        yield session
```

Line by line:

- **URL rewrite** — platforms (Railway included) hand you `postgresql://…`;
  the async engine needs the `+asyncpg` dialect marker. One `replace` makes the
  app deploy-portable.
- **`pool_pre_ping=True`** — before handing out a pooled connection, emit a
  cheap liveness check; a connection killed by a restart/firewall gets replaced
  instead of exploding mid-request. Cheap insurance, standard in production.
- **`pool_size=10, max_overflow=20`** — up to 30 connections *per process*.
  With `--workers 2` that's 60 against Postgres's default `max_connections=100`.
  Being able to do this arithmetic out loud is senior-signal.
- **`expire_on_commit=False`** — after a service commits, route code still reads
  `item.id`/`item.title` from memory; with the default `True`, each access
  would trigger a refresh query — in async code, potentially an
  awaitable-in-the-wrong-place error.
- **`echo=not is_production`** — full SQL logging in dev; you *watch* your N+1s.

### Declarative base and mixins (`app/shared/models.py`)

```python
class Base(DeclarativeBase): pass

class UUIDMixin:
    id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)

class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now())

class SoftDeleteMixin:
    deleted_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
```

- **UUID PKs** — no enumeration, mergeable across environments, generatable
  client-side; the cost (index locality vs bigserial) is a legitimate trade-off
  question — for this workload, irrelevant; at billions of rows, you'd discuss
  UUIDv7.
- **`DateTime(timezone=True)` + `server_default=func.now()`** — timestamps are
  `timestamptz` set by the *database*, so rows inserted outside the ORM are
  still stamped, and there's exactly one clock.
- **Soft delete as a mixin** — every query in the codebase filters
  `deleted_at.is_(None)`; a nightly worker job (`hard_delete_expired`) purges
  rows older than 30 days. Soft delete = recoverability + audit; the tax =
  every query must remember the filter (see gotchas).

### `lazy="raise"` — the N+1 tripwire

```python
class User(Base, UUIDMixin, TimestampMixin, SoftDeleteMixin):
    boards: Mapped[list["Board"]] = relationship(back_populates="owner", lazy="raise")
```

In async SQLAlchemy, implicit lazy loading is a landmine (it wants to do I/O at
attribute access, where you can't `await`). `lazy="raise"` turns any
un-eager-loaded relationship access into an immediate exception — so the N+1
bug fails loudly in development instead of melting the DB in production. Routes
that need relationships must ask for them explicitly (`selectinload`) or query
the columns they need.

### Services own transactions — one query pattern tour (`app/items/services.py`)

```python
async def list_user_items(user_id, db, include_archived=False, limit=None, offset=0):
    q = (
        select(Item)
        .join(Board, Item.board_id == Board.id)
        .where(Board.owner_id == user_id, Item.deleted_at.is_(None), Board.deleted_at.is_(None))
    )
    if not include_archived:
        q = q.where(Item.is_archived.is_(False))
    q = q.order_by(Item.created_at.desc())
    if limit is not None:
        q = q.limit(limit).offset(offset)
    result = await db.execute(q)
    items = list(result.scalars().all())
    await _attach_gift_totals_and_partner(items, db)   # batch enrich — one IN query
    return items
```

Note the composable 2.x `select()` style, the *pair* of soft-delete filters,
and the enrichment helper: instead of touching `item.partner` per row (N+1 —
and `lazy="raise"` would veto it anyway), `_attach_gift_totals_and_partner`
collects the partner IDs and loads them with one `WHERE id IN (…)` query.
That's the N+1 fix pattern, in the wild.

### The crown jewel: atomic reservations (`app/reservations/services.py`)

```python
async def reserve_item(item_id, reserver_id, data, db) -> Reservation:
    result = await db.execute(
        select(Item)
        .where(Item.id == item_id, Item.deleted_at.is_(None))
        .with_for_update()                       # ← row lock
    )
    item = result.scalar_one_or_none()
    if item is None:
        raise NotFoundError("Item not found")
    if item.status != "available":
        raise ConflictError("This item has already been claimed")

    allowed = await can_view_board(reserver_id, item.board_id, db)
    if not allowed:
        raise ForbiddenError("You do not have access to this board")
    ...
    item.status = "reserved"
    reservation = Reservation(item_id=item_id, reserver_id=reserver_id, **data.model_dump())
    db.add(reservation)
    await db.flush()
    ...
    await db.commit()
```

Why this is correct: two concurrent requests both reach
`SELECT … FOR UPDATE`. The first acquires the row lock; the second **blocks**.
First sets `status='reserved'`, commits, releases the lock; second's SELECT now
returns the *committed* row (`status='reserved'`) → `ConflictError` → 409. The
check-then-act race is closed *by the database*, not by hopeful application
logic. Alternatives worth knowing for follow-ups: an optimistic
`UPDATE items SET status='reserved' WHERE id=? AND status='available'` checking
rowcount (no blocking, no ORM object), or a partial unique index on
reservations (`WHERE status='reserved'`) as a belt-and-braces constraint.

Also note `flush()` (not commit) mid-function: the reservation needs its `id`
for the confirmation notification, but everything must stand or fall as one
transaction — one `commit()` at the end.

## How this is used in production

The engine/session/unit-of-work shape here is the canonical production setup.
Real systems add: **pgbouncer** when worker×pool arithmetic outgrows
`max_connections` (know that asyncpg + pgbouncer requires session pooling mode
or care with prepared statements); **read replicas** with a second engine for
heavy reads; **slow-query logging** (`log_min_duration_statement`) tied to the
request-ID from lesson 02. Row locking with `FOR UPDATE` is the standard tool
for inventory/booking systems; at higher contention you'd move to
`FOR UPDATE SKIP LOCKED` queues — the exact mechanism arq-alternatives like
Postgres-backed task queues use.

## Advanced corner

- **One session, one task.** `AsyncSession` is not concurrency-safe; sharing it
  across `asyncio.gather` branches corrupts state. Surwill's refresh job
  (lesson 09) gathers scrapes concurrently but performs all *DB mutation* on
  one session in one task — study that split.
- **Isolation levels:** the reservation logic is correct at READ COMMITTED
  (Postgres default) *because* `FOR UPDATE` re-reads the committed row after
  the lock wait. Under REPEATABLE READ you'd instead see serialization errors
  to retry. Being able to say that sentence is a senior differentiator.
- **`scalar_one_or_none` vs `scalar` vs `scalars().all()`** — one row that must
  be unique / first-or-None / list. Misusing `.scalar()` on multi-row results
  silently drops rows.
- **Where's the repository pattern?** Services call the session directly.
  Testable because tests use a real Postgres; swappable is deferred. Know the
  counter-position (*Architecture Patterns with Python* ch. 2) and argue both.

## Best practices

- Engine per process; session per request/job; commits in services, never routes.
- `pool_pre_ping`, sized pools, `expire_on_commit=False` — the async trinity.
- `lazy="raise"` + explicit eager loads; batch-enrich with IN queries.
- Locks for invariants; soft-delete filters everywhere + reaper job.

## Common mistakes & gotchas

- **Forgetting the soft-delete filter** in a new query — deleted data resurfaces.
  (Mitigation if it bites twice: a default `with_loader_criteria` event.)
- Calling `.commit()` then reading relationship attributes with default expiry
  — works locally (sync), explodes async. `expire_on_commit=False` is why
  Surwill doesn't feel this.
- `await db.refresh(item)` sprinkled reflexively — each is a SELECT; Surwill
  uses it deliberately after commit where the server sets defaults.
- Pool arithmetic ignored → "FATAL: remaining connection slots reserved".

## Where AI helps (and hurts)

AI writes 2.x-style queries well but **defaults to 1.x `session.query()`** if
your prompt has any legacy code in it, and it almost never adds soft-delete
filters or lock clauses unprompted. Concurrency correctness is yours alone.

## Interview Q&A

**Q: Two users reserve the same item at the same instant. Walk me through it.**
A: "Both requests SELECT the item with `FOR UPDATE`. One wins the row lock; the
other blocks inside the database. Winner validates `status='available'`, sets
it to reserved, inserts the reservation, commits — lock released. The loser's
SELECT then completes against the committed row, sees 'reserved', and my
service raises a 409 Conflict. The invariant is enforced by Postgres row
locking at READ COMMITTED, not by application checks that can interleave. The
lock-free alternative is a conditional UPDATE checking rowcount; I chose the
lock because I need the loaded row for permission checks in the same
transaction."

**Q: How do you prevent N+1 queries in an async app?**
A: "Three layers: relationships are declared `lazy='raise'`, so an accidental
lazy access throws immediately in dev; queries that need related rows eager-load
explicitly; and list enrichment is batched — collect IDs, one IN query, stitch
in memory. Async makes this stricter than sync: implicit lazy loads can't even
await, so failing loudly is the only sane configuration."

**Q: How many DB connections can your deployment open?**
A: "pool_size 10 + max_overflow 20 = 30 per process, × 2 uvicorn workers + the
arq worker's engine = up to ~90 theoretical against Postgres's default 100.
That's the number that tells you when pgbouncer becomes non-optional."

## Key takeaways

- Engine = process singleton with pre-ping and sized pool; session = per-request unit of work; `expire_on_commit=False` in async, always.
- Mixins give UUID PKs, DB-side timestamptz, soft delete; every query carries the soft-delete filter.
- `lazy="raise"` converts N+1s into dev-time crashes; batch-enrich with IN.
- `SELECT … FOR UPDATE` closes the reservation race — the project's flagship correctness story.
