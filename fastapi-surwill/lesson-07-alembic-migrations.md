# Lesson 07 — Alembic Migrations

**Track:** FastAPI (Surwill) · **Time:** ~1.5h · **Prerequisites:** lesson 06
**Objectives:** understand `alembic/env.py`, write a migration by hand (using the real `drop otp_codes` one), know autogenerate's limits, and hold the "migrations on deploy" trade-offs.

---

## Why this matters

Schema change is the highest-stakes routine operation in backend work — it
touches every replica, can lock tables, and is hard to undo. "How do you handle
database migrations?" appears in almost every backend interview. Surwill has 22
real migrations, including a feature-removal migration you can narrate.

## Theory

Alembic maintains a **linked list of revisions** (each file has `revision` and
`down_revision`) and a single-row table `alembic_version` in the database
recording the current position. `alembic upgrade head` walks from the recorded
revision to the newest, running each `upgrade()`; `downgrade` walks back.

**Autogenerate** diffs your SQLAlchemy metadata (every model imported into
`env.py`) against the live schema and drafts operations. It is a draft, not a
truth: it detects adds/drops/type changes, but *cannot* see column renames
(sees drop+add — data loss if applied blindly), data backfills, or most
constraint subtleties. Every autogenerated file gets read and edited by a human.

> "Alembic is a lightweight database migration tool for usage with the
> SQLAlchemy Database Toolkit for Python."
> — Alembic docs, https://alembic.sqlalchemy.org/

## The code, explained

### `alembic/env.py` — the two things that matter

```python
from app.config import settings
db_url = settings.DATABASE_URL.replace("postgresql://", "postgresql+asyncpg://", 1)
config.set_main_option("sqlalchemy.url", db_url)

# Import all models so Alembic detects them
from app.shared.models import Base
from app.auth.models import PasswordResetToken, RefreshToken
from app.users.models import User
from app.boards.models import Board
from app.items.models import Item
...
target_metadata = Base.metadata
```

1. **The URL comes from the app's own settings** — migrations run against
   whatever the app would use; no second config to drift.
2. **Every model module is imported** — autogenerate only sees tables whose
   models are imported. Forget an import and autogenerate *drops* that table's
   diff coverage: a new `Notification` model that isn't imported here simply
   never gets a migration. In a vertically-sliced app this import list is the
   one place all slices meet again — same story as `worker.py` in lesson 01.

### A real migration: removing a feature

When phone/OTP auth was removed, the `otp_codes` table went with it:

```python
"""Drop otp_codes — registration no longer uses phone/SMS verification."""

revision = "u1v2w3x4y5z6"
down_revision = "t0u1v2w3x4y5"

def upgrade() -> None:
    op.drop_table("otp_codes")

def downgrade() -> None:
    op.create_table(
        "otp_codes",
        sa.Column("id", postgresql.UUID(as_uuid=True), primary_key=True),
        sa.Column("phone", sa.String(20), nullable=False, index=True),
        sa.Column("code_hash", sa.String(64), nullable=False),
        sa.Column("attempts", sa.Integer(), nullable=False, server_default="0"),
        sa.Column("expires_at", sa.DateTime(timezone=True), nullable=False),
        sa.Column("used", sa.Boolean(), nullable=False, server_default=sa.false()),
        sa.Column("created_at", sa.DateTime(timezone=True), server_default=sa.func.now()),
        sa.Column("updated_at", sa.DateTime(timezone=True), server_default=sa.func.now()),
    )
```

Points to internalize:

- **Docstring says why**, not just what — migrations are the schema's history book.
- **The downgrade rebuilds structure, not data.** Dropped rows are gone;
  `downgrade()` restores the *shape* so the revision chain stays walkable. For
  transient data (OTP codes expire in 10 minutes) that's completely acceptable
  — and saying so is the senior answer. For precious data you'd archive to a
  side table first, or declare the migration irreversible
  (`raise NotImplementedError`) and mean it.
- The model class was deleted from `auth/models.py` **and** its imports fixed
  in `env.py` + `seed.py` in the same commit — model, metadata imports, and
  migration move together or autogenerate starts lying.

### Where migrations run

```dockerfile
CMD ["sh", "-c", "alembic upgrade head && uvicorn app.main:app ..."]
```

Migrate-on-boot: perfect for a single-replica deploy (dev, early Railway) —
the container never serves with a stale schema. The known limits, which
`DEPLOY.md` documents as future work:

1. **Two replicas booting = two concurrent `upgrade head`** — Alembic takes a
   transaction, but DDL races are still possible; the fix is a release phase
   (run migrations once, then roll out) or an advisory lock.
2. **Rollbacks decouple** — rolling back the *code* doesn't downgrade the
   *schema*; that's why the real discipline is…

### Expand → migrate → contract

The zero-downtime pattern every senior interview wants to hear:

1. **Expand:** add the new column/table *nullable/with default*; old code ignores it.
2. **Deploy code** that writes both/reads new with fallback.
3. **Backfill** data (batched, off-peak).
4. **Contract:** a later migration adds constraints / drops the old column,
   after no running code references it.

Surwill's own history shows the shape: `visibility` was added to items with
`server_default 'public'` (expand — old rows valid instantly), and the OTP drop
happened *after* the code stopped referencing the table (contract).

## How this is used in production

Everyone runs Alembic (or its framework twins) in CI: a job asserts
`alembic upgrade head` runs clean against a scratch DB, and some teams assert
"no pending autogenerate diff" so models and migrations can't drift. Big shops
gate DDL by class: additive migrations auto-apply; anything with locks
(`ALTER TABLE … SET NOT NULL`, index builds) goes through review with
`CREATE INDEX CONCURRENTLY` and `lock_timeout` set. GitHub and GitLab both
publish their online-migration playbooks — the expand/contract vocabulary is
universal.

## Advanced corner

- **Locking:** most `ALTER TABLE` takes `ACCESS EXCLUSIVE` — even a
  milliseconds-long one queues behind a long-running query and then blocks
  *everything* behind it. Production discipline: `SET lock_timeout = '2s'` in
  migrations, retry on failure.
- **`CREATE INDEX CONCURRENTLY`** can't run inside a transaction — in Alembic
  that's `op.execute` with `autocommit_block()`. Know that phrase.
- **Branching:** two PRs branching from the same head create two heads;
  `alembic merge` reunites them. CI that runs `alembic heads` and fails on >1
  catches it early (Surwill's single-developer history dodged this; teams don't).
- **SQLite dev mode:** Surwill's `init_db()` uses `create_all` + a tiny
  hand-rolled column-adder for SQLite dev, because Alembic+SQLite's ALTER
  support is limited. Two schema paths is a consciously-carried inconsistency —
  name it before the interviewer does.

## Best practices

- Migration = smallest reviewable unit; docstring explains *why*.
- Read every autogenerated file; assume renames are wrong.
- Expand → migrate → contract for anything a live system touches.
- Keep `env.py` imports complete; CI-run migrations against scratch DB.

## Common mistakes & gotchas

- New model, forgotten `env.py` import → "autogenerate produced nothing."
- Applying an autogenerated "rename" (drop+add) → column data vanishes.
- `NOT NULL` added without default/backfill → boom on first old row.
- Migrate-on-boot with N replicas → racing DDL. One migrator, N servers.

## Where AI helps (and hurts)

AI drafts migration files fast and correctly *for the operations you name*. It
does not know your data volumes or lock sensitivities — it will cheerfully
write a table-rewriting `ALTER` for your billion-row table. Locking analysis
stays human.

## Interview Q&A

**Q: How do you deploy a schema change without downtime?**
A: "Expand-migrate-contract. First an additive migration — new column nullable
or defaulted, so old code keeps running. Then ship code that writes both and
reads the new path. Backfill in batches. Only when nothing references the old
shape does a contract migration drop it or tighten constraints. And every DDL
runs with a lock_timeout, because even an instant ALTER queues behind a slow
query and then blocks the world."

**Q: What does Alembic autogenerate get wrong?**
A: "Renames — it sees a drop plus an add, which is data loss if merged blindly.
It also can't express backfills or know locking impact. I treat its output as a
draft: in my project every migration file was reviewed, and feature-removal
migrations like dropping the OTP table were written by hand with an explicit
structure-only downgrade."

**Q: Where do migrations run in your deployment, and what's the weakness?**
A: "`alembic upgrade head` in the container command before uvicorn starts —
correct-by-construction for one replica. The documented weakness is horizontal
scaling: two replicas would race the upgrade, so the next step is moving it to
a release phase. I'd rather name that limit than pretend it isn't there."

## Exercises against the codebase

- **Easy:** `alembic history | head -25` in the api container; find the OTP
  drop and the migration that added `visibility`, and classify each as
  expand or contract.
- **Medium:** Add a `nickname` column to `users` (nullable) via autogenerate;
  read the generated file critically, tighten it, apply, downgrade, re-apply.
- **Hard:** Write the full expand/contract pair to *rename*
  `items.price_estimate` → `items.price` without downtime: expand migration,
  dual-write code sketch, backfill script, contract migration. (Don't merge it
  — the point is the choreography.)

## Key takeaways

- Alembic = revision linked-list + `alembic_version` pointer; autogenerate is a draft.
- `env.py` must import every model — the metadata is only what it can see.
- Migrate-on-boot is fine at one replica; a release phase is the scale-up path.
- Expand → migrate → contract is the answer to every zero-downtime schema question.
